Vibe Coding 必备的 5 个对抗式审查 Prompt：让 AI 自己挑自己的刺

一、你有没有被 AI"顺着写"坑过？

Vibe Coding 写久了，你会发现一个特别隐蔽的问题：AI 太会顺着你了。

你说"帮我写个登录接口"，它 5 秒就给你一个能跑的版本。你说"这个 Bug 帮我修一下"，它立刻给你打补丁。你问"这个方案怎么样"，它回复"很好，结构清晰、考虑周到、风险可控"。

听上去很爽，但用过几次你就会发现——

  • 登录接口里密码居然是明文存的，AI 没提醒你。
  • Bug 修了，但根本原因没找到，下次换个场景又爆。
  • 方案"看起来很美"，但落地后性能一塌糊涂，AI 那时候已经收工了。

问题不在 AI，在你给它的指令。

之前看 数字生命卡兹克open in new window 的文章（《分享 2 个 Vibe Coding 必备的超实用 Prompt》open in new window），他把 Vibe Coding 总结成两件事：

前者管生成，后者管验证。第一性原理 + 对抗式审查。

第一性原理我懂，就是平时咋说咋说，最后加一句"从第一性原理出发"——强制打断 AI 的类比推理，逼它回到问题本质去思考。

但对抗式审查这件事，我自己用了大半年才真正理解它的威力。

这篇文章我就把"对抗式审查"这个概念，拆成 5 个真正能用的 Prompt 模板，再给一套落地到 Cursor / Claude Code 的工程做法，最后用一个 Express API 重构的真实案例 walk through。

照着抄就能用。

特别注意 本文所有 Prompt 模板，灵感来自卡兹克的"对抗式审查"思路和社区朋友们的二次创作。我做了重新组织 + 工程化封装，核心是"让 AI 站到反面挑刺"，不是空泛的"帮我 review 一下"。

二、什么是对抗式审查？一句话讲透

对抗式审查：在 Vibe Coding 流程里，主动让 AI 跳出"帮你写"的角色，站到反面挑刺。

它跟"帮我看看有没有问题"的本质区别是：

维度普通"帮我 review"对抗式审查
AI 角色你的助手你的反方辩手
默认立场"应该没问题""假设它会失败"
输出倾向温和建议刺耳的、具体的反对意见
触发时机写完之后写之前、写中、写后都可以
关键句式"看看有没有问题""假设它失败了，找出 5 个原因"

特别注意 "对抗式"不是让你跟 AI 吵架。它的本质是给 AI 一个明确的反方角色 + 具体的反方剧本，逼它输出你平时听不到的"刺耳答案"。

三、5 个对抗式审查 Prompt 模板

下面是我日常在用的 5 个模板。每个都能直接复制粘贴，替换 <> 里的内容就能用。

先说明一下：这 5 个都是手动触发的提问模板——你在对应场景下主动把它发给 AI。哪些适合固化进规则文件、哪些只适合手动用，第四节开头有一张对应表。

3.1 需求拆解型：让 AI 拆你的假设

适用场景：产品想法刚冒出来，准备让 AI 帮你出方案时。

先别急着给答案。请把这个问题拆回最底层：

1. 我真正想解决的是什么？（用一句话说，别用行业黑话）
2. 这里有哪些未经验证的假设？列 3-5 个。
3. 如果不用常见套路，还有没有更短的路径？
4. 今天最小能验证的一步是什么？

要求：先拆解，不要给方案。等我确认完假设再继续。

为什么有效： 卡兹克原话——"这个需求可能不够痛。"或者"用户也许只需要一个表格模板，不需要一个工具。"这种话不好听，但比一页漂亮路线图更值钱。

真实使用前后对比：

普通问法对抗式问法
"帮我设计一个 AI 简历筛选工具的 MVP"用上面的模板先拆
AI 立刻给出 8 个功能、3 个数据源、1 个商业模式AI 先列出 5 个未验证假设：① 招聘官真的在意 AI 筛选吗？② 简历结构化是高频痛点还是低频？③ 现有 ATS 工具为什么没做？④ 我能拿到合规的训练数据吗？⑤ 客户付费意愿到底是工具还是结果？

特别注意 这个模板最大的价值是强制 AI 在写代码之前，先告诉你"哪些前提可能是错的"。很多 Vibe Coding 项目的死法，是"产品想法本身不成立"，不是"代码写得差"。

3.2 Bug 修复型：让 AI 先解释机制再动手

适用场景：让 AI 修 Bug，但你不确定它是不是"打补丁式修复"。

先不要改代码。请先回答三个问题：

1. 这个系统本来应该怎么运转？（用 200 字讲清楚数据流）
2. 当前现象违反了哪条机制？（不要只看报错，看更深一层的状态）
3. 如果只做表层修复（比如加个 fallback / 包个 retry / 加个 if），后面最可能在哪继续出问题？

回答完这三个问题之后，**再**给最小修改点。

为什么有效： Vibe Coding 修 Bug 最常见的死法是"治标不治本"。AI 看到 TypeError: Cannot read property 'x' of undefined，立刻给你加一个 if (x)，跑通了你就 merge。半年后另一个场景触发类似的问题，你才发现根因在数据结构上。

真实使用前后对比：

普通问法对抗式问法
"用户登录报 TypeError，帮我修"用上面的模板
AI 加一个 if (user) 兜底，Bug 消失AI 先回答：① 登录流程是"前端调 /api/login → 后端查 user → 返回 token"，user 不存在时本应返回 401，前端在 catch 里应该跳转登录页② 违反了"前端必须处理 401 并清理本地 token"这条契约③ 表层修法（加 if）会让前端一直卡在"半登录"状态，但用户已经看到登录态，真正的修复是前端加 401 拦截 + 自动登出然后给最小修改点

3.3 代码审查型：让 AI 站到反面挑刺

适用场景：写完一段代码，准备提交前。

现在请站到反面来审这段代码。假设它最后在生产环境失败了，帮我找出：

1. 哪类输入根本没考虑过？（列 3 个具体场景）
2. 哪个分支逻辑是"看起来对"但其实没被测试覆盖的？
3. 哪个边界条件会让它性能暴跌或死循环？
4. 哪段代码在并发/重试/超时场景下会出问题？
5. 哪种使用方式会让它被误用？（比如错误的调用顺序）

回答要具体到行号或函数名，不要给"建议加强错误处理"这种空话。

为什么有效： "帮我 review 一下"AI 通常给"结构清晰、命名规范、考虑周到"——等于没说。 对抗式版本逼它假设失败、列出具体场景、定位具体行号。这种 review 才有用。

一个真实例子：

// 你的代码
async function getUser(id) {
  const user = await db.query('SELECT * FROM users WHERE id = ?', [id]);
  return user;
}

AI 用对抗式审查给的反馈：

① id 为字符串时 db.query 可能因类型转换出错（PostgreSQL 报 invalid input syntax） ② db.query 返回 undefined 时（连接池满），下面任何属性访问都会炸 ③ 高并发下 N+1 查询会让 DB 直接挂 ④ 没超时控制，一个慢查询能卡住整个 event loop ⑤ 调用方传 null 时 WHERE id = NULL 永远查不到，应该抛错而不是返回空

这种反馈才是 review。

3.4 方案对比型：让 AI 互啄

适用场景：在两个技术方案之间犹豫不决。

我现在要在 <方案 A：XXX> 和 <方案 B：XXX> 之间选一个。

请扮演方案 A 的最强支持者，写一段 200 字的辩护，**只讲优点**。
然后请扮演方案 B 的最强支持者，再写一段 200 字的辩护，**只讲优点**。
然后告诉我：
- 哪个方案的"独有优势"是另一个方案无论如何都做不到的？
- 哪个方案看起来光鲜但其实有一个隐藏的"决策税"（未来 6 个月会还的债）？
- 如果只能选一个，**在 6 个月后回看**，哪个更可能让我后悔？

最后再给我结论。

为什么有效： 让 AI "客观对比"通常是废话——它会列一堆优缺点，最后说"取决于你的具体场景"。对抗式版本逼它先全力支持 A，再全力支持 B，最后才比较。这种辩论过程里它会暴露一些它原本不会主动说的东西。

3.5 文档/PRD 审查型：让 AI 当你的第一个杠精用户

适用场景：写完产品 PRD、API 文档、用户文案，准备对外发布。

现在请扮演一个**典型但挑剔的目标用户**。你的画像是：

- 30 岁，非技术背景
- 日常工作里用过 3-5 个类似产品
- 时间很紧，看文档超过 2 分钟就走

请通读下面的文档/PRD，回答：

1. 哪个段落让你想关掉页面？（具体到那句话）
2. 哪个功能你看完不知道"对我有啥用"？
3. 哪个步骤你会卡住、不知道下一步点哪里？
4. 哪个术语让你觉得"作者在装 X"？
5. 如果只能保留 3 个功能，你会砍哪 2 个？为什么？

要刻薄，不要客气。

为什么有效： 大多数 PRD 写完都觉得"挺清楚的"——因为你脑子里有完整上下文。目标用户脑子里啥都没有。这个模板逼 AI 模拟一个"零上下文 + 没耐心"的真实用户，给你的反馈比"前辈 review"准。

四、怎么把对抗式审查集成到 Cursor / Claude Code

光有 Prompt 模板还不够。真正能改变工作流的，是把它写进规则文件，让 AI 主动触发。

但先想清楚一个问题：5 个模板是不是都要塞进规则文件？不是。 规则文件是 always-on 的——每次生成代码都会触发。3.1（拆需求）、3.2（修 Bug）、3.4（方案选型）都是特定场景才需要的，固化进规则文件会乱触发、白烧 token。真正适合进规则文件的，只有 3.3 这个通用代码审查层。

对应关系一张表讲清楚：

模板触发时机使用方式
3.1 需求拆解动手写代码之前手动
3.2 Bug 修复排查 Bug 时手动
3.3 代码审查每次写完代码进规则文件（下面 4.1 / 4.2 就是它的压缩版）
3.4 方案对比两个方案犹豫不决时手动
3.5 文档审查文档对外发布前手动；如果你的项目以文档为主，可以仿照 4.2 写进规则文件

特别注意 下面 4.1 和 4.2 的规则模板不是让你原样复制的。它们只是示例骨架——触发条件、审查问句、输出要求都要按你自己的项目改。比如你主要写文档，就把审查问句换成 3.5 那组；你经常做方案选型，可以把 3.4 的"决策税"追问加进去。规则留一点模糊是故意的，因为每个人的项目情况不同。

4.1 Cursor：写到 .cursorrules

在项目根目录新建 .cursorrules，加入（这就是 3.3 模板的压缩版——把 5 个追问压成"列 3 个失败场景"，方便每次自动跑）：

# 每次生成代码后自动触发对抗式审查
after_code_generation:
  - role: "adversarial_reviewer"
    trigger: "always"
    prompt: |
      请扮演代码反方审查员。假设这段代码会在生产环境失败，
      列出 3 个最可能被触发的失败场景，每个场景给出：
      1. 触发条件（具体输入 / 并发 / 时序）
      2. 代码里对应的薄弱位置（行号或函数名）
      3. 最小修复建议

      不要说"代码看起来不错"，直接给刺耳意见。

这样每次 Cursor 写完代码，它会自动跑一遍反方审查，相当于自带一个 reviewer。

特别注意 上面的 YAML 结构是示意写法，重点是 prompt: 里那段话。Cursor 规则文件本质是自然语言指令，你可以直接把那段提示词原样贴进 .cursorrules（新版是 .cursor/rules/*.mdc），不用纠结字段名。

4.2 Claude Code：写到 CLAUDE.md

在项目根目录建 CLAUDE.md（注意：这个模板是混合改写——问句 1、2 来自 3.3，问句 3 借了 3.4 的"决策税"视角，问句 4 借了 3.5 的"砍功能"视角，你同样可以按自己项目重新组装）：

# 项目规则

## 强制审查规则

每次你完成以下任务后，**必须**自动追加一次对抗式审查：

- ✅ 写完一个新函数 / 类 / 模块
- ✅ 修完一个 Bug
- ✅ 改完一个配置文件
- ✅ 写完一段 PRD / 文档

## 审查模板

请用以下模板，**只输出反方意见，不要给正面反馈**：

1. 哪类输入 / 场景没考虑过？
2. 哪个分支逻辑是"看起来对"但其实没覆盖？
3. 未来 6 个月内最可能在哪里出问题？
4. 如果只保留一半功能，应该砍哪一半？

输出要求：具体到行号 / 函数名 / 段落，**禁止说"代码看起来不错"**。

效果：Claude Code 每写完一段代码，会自动追加一段反方审查输出。你不用每次都手动说"现在请站到反面"。

4.3 对接 Anthropic Console / Promptfoo 做离线评估

如果你是团队作战，建议把第三节的 5 个模板（requirement 对应 3.1、bugfix 对应 3.2、review 对应 3.3、compare 对应 3.4、doc 对应 3.5）固化成测试集：

// promptfoo 配置示例
{
  prompts: [
    "prompts/adversarial_requirement.md",
    "prompts/adversarial_bugfix.md",
    "prompts/adversarial_review.md",
    "prompts/adversarial_compare.md",
    "prompts/adversarial_doc.md"
  ],
  tests: [
    {
      assert: [
        { type: "contains", value: "假设它失败" },
        { type: "not-contains", value: "看起来不错" },
        { type: "javascript", value: "output.split('\\n').length >= 5" }
      ]
    }
  ]
}

特别注意 这个配置的核心是 not-contains: "看起来不错"——把"温和无用的反馈"在 CI 阶段就拦掉，逼模型必须输出具体的反方意见。

五、真实场景 walk through：重构一个 Express API

光说不练假把式。下面用一段真实的 Vibe Coding 流程，演示对抗式审查怎么用。

5.1 初始需求

我："帮我写一个用户列表接口，路径 /api/users，支持分页和按 name 模糊搜索。用 Express + Prisma。"

AI 给了一版代码（节选）：

app.get('/api/users', async (req, res) => {
  const { page = 1, pageSize = 20, name } = req.query;
  const where = name ? { name: { contains: name } } : {};
  const users = await prisma.user.findMany({
    where,
    skip: (page - 1) * pageSize,
    take: Number(pageSize)
  });
  res.json({ users });
});

跑了一下，能用，但你不放心。

5.2 触发对抗式审查

你："现在请站到反面来审这段代码。假设它最后在生产环境失败了，帮我找出 5 个最可能的失败点，每个要具体到行号。"

AI 反馈：

① pageSize 没上限，攻击者传 ?pageSize=99999999 会让 DB 一次查几百万行（第 5 行） ② name 没做 SQL 注入防护，虽然 Prisma 默认防，但 contains 在 SQLite 下会被关闭（第 4 行） ③ Number(pageSize) 遇到非数字字符串会返回 NaN，Prisma 会抛错（第 6 行） ④ 没返回 total，前端没法做分页器（第 8 行） ⑤ name 是大小写敏感的，搜索"张"搜不到"ZHANG"开头的（第 4 行）

5.3 触发第一性原理（如果审查后还有疑问）

你："从第一性原理出发，'分页 + 模糊搜索'这个接口最该考虑的设计约束是什么？"

AI 回答：

从第一性原理看，分页 + 模糊搜索有 3 个本质约束： ① 性能：分页必须能利用索引（skip 越大越慢，深分页用 keyset 而不是 offset） ② 一致性：模糊搜索 + 分页，并发新增数据会导致重复或漏行 ③ 可用性：name 模糊搜索本质是字符串相似度问题，contains 是最弱的，应该有 relevance score

当前实现只解决了"能返回数据"，3 个本质约束一个都没满足。

5.4 让 AI 重写并明确 trade-off

你："按上面 3 个本质约束重写，但要明确告诉我每个约束的取舍（比如深分页用 keyset 改不了并发一致性）。"

最终版（节选）：

app.get('/api/users', async (req, res) => {
  const { page = 1, pageSize = 20, name, cursor } = req.query;

  // 防御：限制 pageSize
  const limit = Math.min(Number(pageSize) || 20, 100);

  const where = name ? { name: { contains: name, mode: 'insensitive' } } : {};

  // 深分页用 cursor
  if (cursor) {
    const users = await prisma.user.findMany({
      where,
      cursor: { id: Number(cursor) },
      skip: 1,
      take: limit,
      orderBy: { id: 'asc' }
    });
    return res.json({
      users,
      nextCursor: users.length === limit ? users[users.length - 1].id : null
    });
  }

  // 浅分页用 offset
  const [users, total] = await Promise.all([
    prisma.user.findMany({ where, skip: (page - 1) * limit, take: limit }),
    prisma.user.count({ where })
  ]);

  res.json({ users, total, page: Number(page), pageSize: limit });
});

5.5 总结：这一轮走完，AI 输出从"能跑"变成"能上生产"

阶段耗时产出
普通 Vibe Coding30 秒一个能跑但不安全的接口
+ 对抗式审查+ 1 分钟5 个具体反方意见
+ 第一性原理追问+ 1 分钟3 个本质约束
+ 重写 + trade-off 明确+ 2 分钟能上生产的接口

多花了 4 分钟，但你省下了生产环境半夜被叫醒的时间。

六、6 个常见误区（以及怎么避免）

6.1 误区 1："帮我看看有没有问题"

这是最常见也最没用的指令。AI 默认会"找小问题 + 给温和建议"。

正确做法：用 3.3 的反方模板，明确"假设失败、列具体场景"。

6.2 误区 2：审查完就 merge

反方审查是找到问题，不是修完问题。修之前还要追问"为什么之前没想到"。

正确做法：审查后追问一句"这 5 个问题里，哪个是最底层、最该现在修的？"。

6.3 误区 3：所有任务都上对抗式审查

对抗式审查有 token 开销。写 hello world 不需要反方审查。

正确做法：只在改动 > 50 行、跨多个文件、涉及线上逻辑这三种情况下用。

6.4 误区 4：只审查代码不审查需求

很多项目死在"产品想法本身不成立"。

正确做法：写代码前先用 3.1 拆需求，需求层就拦掉一半死法。

6.5 误区 5：把"反方意见"当真

AI 提的失败场景有概率是它编的。要结合自己项目的实际流量、用户量、并发量判断。

正确做法：每个反方意见问一句"我这个项目真的会触发这个场景吗？"。不触发的不修。

6.6 误区 6：对抗式审查 = 找茬

它的目的不是让 AI 跟你吵架，是逼 AI 暴露它本来会藏起来的盲区。

正确做法：把反方意见当作"补充视角"，不是"攻击"。

七、对比：传统 Vibe Coding vs 对抗式 Vibe Coding

维度传统 Vibe Coding对抗式 Vibe Coding
AI 角色助手助手 + 反方
默认立场顺着你假设你错了
反馈质量温和但无用刺耳但具体
适用任务简单 CRUD / 原型生产逻辑 / 重构 / 方案选型
Token 消耗1x1.5-2x（多一轮审查）
上生产返工率高低 30-50%
心智负担低中（要消化反方意见）

八、总结

Vibe Coding 不是"让 AI 写完你就 merge"。它是一个"生成 + 验证"的闭环。

第一性原理负责"生成侧"——逼 AI 从本质思考，不抄套路。 对抗式审查负责"验证侧"——逼 AI 暴露盲区，不放过潜在问题。

把这两件事写进 .cursorrules / CLAUDE.md，让 AI 自动触发，你的 Vibe Coding 流程就从"碰运气"变成"工程化"。

5 个 Prompt 模板都在第三节，复制粘贴就能用。

最后送你一句话——来自博主卡兹克的博客原文：

"前者管生成，后者管验证，基本能保证你在 Vibe Coding 的时候，写出来的代码和最后的运行，有质的飞跃。"

下次写完代码前，记得让 AI 站到反面挑一次刺。
